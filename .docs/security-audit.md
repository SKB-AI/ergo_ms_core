# Аудит безопасности ядра

Документ описывает состояние безопасности ядра ERGO MS по результатам проверки исходного кода **4 августа 2026 года**. Он предназначен для разработчиков ядра и для тех, кто отвечает за развёртывание системы на сервере: по каждой находке указано, где расположен код, чем именно опасно текущее поведение и что нужно изменить.

Проект градации режимов безопасности, которая позволит закрывать эти находки не точечно, а выбором уровня в `.env`, описан отдельно — [Режимы безопасности](security-modes.md). В последнем разделе этого документа находки сопоставлены с контролями режимов.

## Что проверялось

Проверка охватывает **только ядро**:

| Часть | Что смотрели |
|---|---|
| `core/api` | настройки Django и DRF, аутентификация, сессии устройств, права доступа (ADP), аудит, мессенджер, уведомления, realtime |
| `core/client` | хранение токенов, обновление сессии, логирование ошибок |
| `core/media_api` | подпись ссылок, загрузка файлов, внутренний API, заголовки ответов |
| `core/deployment` | шаблоны `.env`, nginx, Redis, Docker Compose, режимы `ERGO_*` |

Границы проверки, о которых важно помнить:

- **Модули** в каталоге `modules/` не проверялись — у каждого модуля свой набор представлений и прав.
- Не выполнялись **проверка зависимостей** на известные уязвимости и **тестирование на проникновение**; выводы сделаны по чтению кода.
- Не проверялась инфраструктура конкретной установки: реальные значения `.env`, правила межсетевого экрана, права на файлы на сервере.

## Сводка

Найдено 3 критичных, 7 высоких, 11 средних и 7 низких по значимости отклонений.

Три главных риска, которые стоит закрывать в первую очередь:

1. **Массовое создание учётных записей доступно любому вошедшему пользователю** — импорт пользователей не проверяет права администратора (К1).
2. **Отзыв сессии устройства не работает на большей части эндпоинтов** — базовый класс представлений заменяет аутентификацию с привязкой к устройству на обычную (К2).
3. **Шаблоны конфигурации содержат рабочие значения секретов** — установка, развёрнутая «как есть», подписывает токены и ссылки на файлы предсказуемым ключом (К3).

Дальше по значимости идут неработающее ограничение частоты попыток входа (В1) и разрешающее поведение по умолчанию в мессенджере и на WebSocket (В3, В4).

## Критичные находки

### К1. Импорт пользователей доступен любому вошедшему пользователю

**Где:** [core/api/src/core/cms/adp/views_import.py](../core/api/src/core/cms/adp/views_import.py), строки 33, 166, 280, 292.

Четыре представления импорта наследуют `BaseAPIViewAuthMixin`, то есть требуют только факта входа в систему:

```python
class ImportUsersView(MediaApiFileMixin, BaseAPIViewAuthMixin):
```

**Чем опасно.** Любой пользователь с самой обычной ролью может загрузить файл и создать произвольное количество учётных записей с известными ему паролями, а затем войти под ними. Это прямой путь к повышению привилегий и к рассылке приветственных писем от имени системы. Дополнительно `ImportUsersTaskStatusView` возвращает состояние фоновой задачи по её идентификатору без проверки, кто эту задачу запускал.

**Как исправить.** Заменить базовый класс на `BaseAPIViewGlobalAdminMixin` из [core/api/src/core/utils/base/base_views.py](../core/api/src/core/utils/base/base_views.py) для всех четырёх представлений. Для представления состояния задачи дополнительно сверять инициатора — так, как это уже сделано при выдаче паролей в `import_users_passwords.py`.

**Исправлено.** Все четыре представления переведены на `BaseAPIViewGlobalAdminMixin`; `ImportUsersTaskStatusView` дополнительно сверяет `initiated_by_user_id` из состояния задачи с текущим пользователем (закрывает и С1).

### К2. Базовый класс представлений отключает привязку сессии к устройству

**Где:** [core/api/src/core/utils/base/base_views.py](../core/api/src/core/utils/base/base_views.py), строка 22.

Глобально в настройках DRF задана аутентификация с проверкой устройства:

```python
# core/api/src/config/settings/auth.py, строки 35-37
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'src.core.cms.adp.authentication.DeviceBoundJWTAuthentication',
    ],
```

Но базовый класс, от которого наследуется большинство представлений ядра, переопределяет её на обычную:

```python
# core/api/src/core/utils/base/base_views.py, строки 22-24
    authentication_classes = [JWTAuthentication]
    throttle_classes = [AnonRateThrottle, UserRateThrottle]
    permission_classes = [AllowAny]
```

**Чем опасно.** `DeviceBoundJWTAuthentication` — единственный механизм, который делает выданный access-токен недействительным раньше срока: он требует claim `device_id` и проверяет, что сессия устройства ещё активна. На всех представлениях, унаследованных от `BaseAPIView` (около двадцати файлов: профиль, управление пользователями, импорт, приглашения, присутствие, начальная загрузка сессии), эта проверка не выполняется. В результате кнопка «завершить сеанс на устройстве» и массовый отзыв сессий администратором не закрывают доступ немедленно — украденный access-токен продолжает работать до истечения срока, а это до 30 минут в обычном режиме и **до трёх суток** при входе с «запомнить меня». Приостановка учётной записи при этом продолжает действовать, потому что SimpleJWT сам проверяет признак активности пользователя.

**Как исправить.** Убрать переопределение `authentication_classes` в `BaseAPIView`, чтобы действовала общая настройка. Если для публичных эндпоинтов входа нужна аутентификация без требования `device_id`, объявить её отдельным классом и указывать точечно только там, где это действительно нужно.

**Исправлено.** Переопределение убрано — `BaseAPIView` наследует `DeviceBoundJWTAuthentication` из `DEFAULT_AUTHENTICATION_CLASSES`. Точечное исключение оставлено только на `LogoutView` (plain `JWTAuthentication`), чтобы выход из системы очищал cookie и при уже отозванной сессии устройства.

### К3. Шаблоны конфигурации содержат рабочие значения секретов

**Где:** [.env.example](../.env.example) строка 80, [env/mcp.env.example](../env/mcp.env.example) строки 5–6, [databases.yaml.example](../databases.yaml.example).

```dotenv
API_SECRET_KEY=secret_key
ADMIN_LOGIN=admin
ADMIN_PASSWORD=admin
```

**Чем опасно.** При первичной настройке `setup-full` создаёт `.env` из шаблона, и установка стартует со значением `secret_key`. Этим же ключом по умолчанию подписываются JWT (`API_JWT_SIGNING_KEY` пуст — берётся `API_SECRET_KEY`) и ссылки на файлы в media_api. Знание ключа позволяет выпустить токен от имени любого пользователя, подделать подписанную ссылку на файл и сформировать токен загрузки. Проверка `validate_production_config` в media_api выдаёт лишь предупреждение и не останавливает запуск.

**Как исправить.** Оставить в шаблонах пустое значение и подсказку `ergoms generate-secret`, а при `ERGO_ENV=production` прерывать запуск, если ключ пустой, совпадает с шаблонным или короче безопасной длины. Учётные данные MCP вынести из шаблона в обязательный шаг настройки.

## Высокие находки

### В1. Ограничение частоты попыток входа не действует

**Где:** [core/api/src/core/cms/adp/views_auth.py](../core/api/src/core/cms/adp/views_auth.py) строки 124, 202, 374; [core/api/src/config/settings/auth.py](../core/api/src/config/settings/auth.py) строки 42–51.

Представления входа и восстановления пароля объявляют `throttle_scope = 'login'` и `'password_reset'`, а в настройках для этих областей заданы ограничения `5/minute`. Однако класс `ScopedRateThrottle`, который единственный умеет читать `throttle_scope`, не подключён ни глобально, ни в самих представлениях — поиск по `core/api/src` не находит ни одного упоминания.

**Чем опасно.** Фактически действует общий лимит для гостей: 10 запросов в минуту по умолчанию в коде и **100 запросов в минуту** в шаблоне `.env.example`. Этого достаточно для подбора паролей и кодов восстановления. Ограничение считается по IP-адресу, поэтому распределённый подбор ограничен ещё слабее.

**Как исправить.** Добавить `rest_framework.throttling.ScopedRateThrottle` в список классов ограничения на этих представлениях (либо в общие настройки) и снизить лимит для гостей в шаблоне.

**Исправлено.** `ScopedRateThrottle` подключён на `UserAuthorizationView`, `SendConfirmationCodeView` и `ResetPasswordView` — теперь для входа и восстановления пароля действует лимит `5/minute` из `throttle_scope`, а не только общий anon-лимит. Лимит для гостей в `.env.example` снижен с `100/minute` до `20/minute`.

### В2. Восстановление пароля: короткий код без срока годности и без лимита попыток

**Где:** [core/api/src/core/cms/adp/views_auth.py](../core/api/src/core/cms/adp/views_auth.py), представления отправки кода, проверки кода и сброса пароля.

Код подтверждения — шесть цифр, у модели `EmailConfirmationCode` есть поле времени создания, но срок годности нигде не проверяется. Представление проверки кода не имеет собственного ограничения частоты. Кроме того, при самостоятельной смене или сбросе пароля сессии пользователя не отзываются, тогда как при сбросе пароля администратором вызывается `revoke_user_auth`.

**Чем опасно.** Миллион вариантов кода при 100 запросах в минуту перебирается за ограниченное время, а бессрочный код остаётся действительным неограниченно долго. Если пароль меняют из-за подозрения на компрометацию, у злоумышленника сохраняются рабочие токены.

**Как исправить.** Ввести срок годности кода и счётчик неудачных попыток с блокировкой, подключить отдельное ограничение частоты на проверку кода, вызывать отзыв сессий при любой смене пароля с сохранением текущей сессии инициатора.

**Исправлено.** Код восстановления: TTL 15 минут (`API_PASSWORD_RESET_CODE_TTL_MINUTES`), максимум 5 неверных попыток (`API_PASSWORD_RESET_CODE_MAX_ATTEMPTS`), единый безопасный ответ при ошибке/истечении/блокировке. На `VerifyConfirmationCodeView` подключены `AnonRateThrottle` + `ScopedRateThrottle` (`password_reset`). После самостоятельного сброса — полный `revoke_user_auth`; после смены пароля в профиле — revoke с сохранением текущего устройства (`except_device_id`). Публичные настройки отдают `password_reset_available` только если фича включена и исходящая почта готова; иначе ссылка «Забыл пароль» скрыта, Send отвечает 403 без попытки отправки.

### В3. Мессенджер разрешает доступ по умолчанию

**Где:** [core/api/src/core/messenger/access.py](../core/api/src/core/messenger/access.py), строки 30–32.

```python
    if hasattr(obj, 'has_messenger_access'):
        return obj.has_messenger_access(user)
    return True
```

**Чем опасно.** Если модель, к которой привязано обсуждение, не реализовала метод проверки доступа, читать и писать сообщения может любой вошедший пользователь, знающий тип содержимого и идентификатор объекта. Идентификатор здесь — обычный первичный ключ, то есть перебираемый. Поведение «по умолчанию разрешено» опасно тем, что новый модуль получает уязвимость молча, просто забыв объявить метод.

**Как исправить.** Изменить значение по умолчанию на запрет и требовать явного объявления метода у моделей, которые подключают обсуждения.

**Исправлено.** Без callable `has_messenger_access` на объекте доступ запрещён (`return False`). Исключение в методе модели тоже даёт отказ (fail-closed). REST, WebSocket и SSE topic используют одну функцию в `access.py`.

### В4. Проверка токена на WebSocket слабее, чем в REST

**Где:** [core/api/src/core/cms/adp/ws_auth.py](../core/api/src/core/cms/adp/ws_auth.py), строки 20–32; [core/api/src/config/asgi.py](../core/api/src/config/asgi.py), строки 35–40.

Токен разбирается через `UntypedToken`, который проверяет подпись и срок, но не проверяет тип токена, не требует `device_id` и не сверяется с активностью сессии устройства. В маршрутизации ASGI отсутствует `AllowedHostsOriginValidator`.

**Чем опасно.** На WebSocket принимается в том числе refresh-токен, а отзыв сессии устройства на соединение не влияет. Отсутствие проверки источника означает, что соединение может быть инициировано страницей на постороннем домене; сам по себе токен при этом остаётся необходимым, но защитный слой, предусмотренный Channels, не задействован.

**Как исправить.** Использовать `AccessToken` вместо `UntypedToken`, повторить проверку устройства из `DeviceBoundJWTAuthentication` и обернуть маршрутизатор WebSocket в `AllowedHostsOriginValidator`.

**Исправлено.** `user_from_jwt_token` принимает только `AccessToken` с обязательным `device_id` и активной сессией устройства (как REST). В `asgi.py` WebSocket обёрнут в `AllowedHostsOriginValidator`.

### В5. Redis работает без пароля, а в Docker порт публикуется наружу

**Где:** [core/deployment/redis/redis.conf.template](../core/deployment/redis/redis.conf.template), [databases.yaml.example](../databases.yaml.example), конфигурация Docker Compose.

В шаблоне конфигурации есть `bind` и `protected-mode yes`, но нет `requirepass`. В Docker порт Redis публикуется на хост автоматически, если он свободен.

**Чем опасно.** Redis используется как брокер задач Celery, кэш и слой каналов. Доступ к нему без пароля даёт возможность читать содержимое кэша (включая права и меню), ставить задачи в очередь и подделывать события realtime. При публикации порта защита сводится к настройкам межсетевого экрана машины.

**Как исправить.** Добавить пароль в шаблон и в секцию `redis` файла `databases.yaml`, не публиковать порт на хост без явного запроса.

### В6. Сроки жизни токенов можно отключить, ротация refresh выключена

**Где:** [core/api/src/config/settings/auth.py](../core/api/src/config/settings/auth.py), строки 76–99.

Значение `API_JWT_LIFETIME_ENABLED=false` подставляет срок жизни 5 256 000 минут, то есть около десяти лет. Ротация refresh-токенов отключена (`ROTATE_REFRESH_TOKENS: False`) при установленном приложении чёрного списка. Выход из системы очищает cookie, но не заносит refresh-токен в чёрный список.

**Чем опасно.** Утёкший refresh-токен остаётся рабочим весь срок жизни, а при отключённом ограничении срока — практически бессрочно. Выход из системы не даёт того эффекта, которого от него ожидает пользователь.

**Как исправить.** Включить ротацию с занесением предыдущего токена в чёрный список, заносить refresh-токен в чёрный список при выходе, запретить отключение сроков жизни вне режима разработки.

**Исправлено.** `ROTATE_REFRESH_TOKENS=True` при `BLACKLIST_AFTER_ROTATION=True`; после ротации `DeviceBoundTokenRefreshSerializer` перепривязывает `UserDevice.outstanding_token_jti` через `bind_device_to_refresh_token`. `LogoutView` вызывает `revoke_logout_session` (устройство → blacklist jti), оставаясь идемпотентным (204 + очистка cookie). `API_JWT_LIFETIME_ENABLED=false` в production прерывает запуск (`ImproperlyConfigured`). Контроли `token.lifetime_required`, `token.rotate_refresh`, `token.revoke_on_logout` на уровне `standard` отражают это поведение.
### В7. В production могут остаться разрешения источников для разработки

**Где:** [core/api/src/config/settings/cors.py](../core/api/src/config/settings/cors.py), строки 20–37.

Если переменная `CORS_ALLOWED_ORIGINS` не задана, подставляется список из двенадцати адресов вида `http://localhost:5173` и `http://127.0.0.1:8000`. Проверка окружения при этом не выполняется, а `CORS_ALLOW_CREDENTIALS` включён.

**Чем опасно.** На сервере, где переменную забыли заполнить, браузер разрешит запросы с учётными данными со страницы, открытой на локальном адресе разработчика. Это ослабляет защиту от запросов с посторонних источников.

**Как исправить.** Подставлять адреса для разработки только при `ERGO_ENV=development`, а в production требовать явный список и прерывать запуск при его отсутствии.

**Исправлено.** Localhost-origins подставляются только при `is_development()`. В production без `CORS_ALLOWED_ORIGINS` и без `CORS_ALLOWED_ORIGIN_REGEXES` запуск прерывается (`ImproperlyConfigured`). При nginx публичный origin по-прежнему добавляется через `effective_cors_origins`, без смеси с localhost.

## Средние находки

### С1. Состояние фоновой задачи импорта доступно постороннему

`ImportUsersTaskStatusView` в [views_import.py](../core/api/src/core/cms/adp/views_import.py) (строка 166) принимает идентификатор задачи и возвращает её состояние без проверки инициатора. Идентификаторы задач непредсказуемы, поэтому риск ограничен, но утечка хода импорта и сообщений об ошибках возможна. Проверять инициатора так же, как при выдаче паролей.

### С2. Не задан список доверенных источников для защиты от подделки запросов

В настройках нет `CSRF_TRUSTED_ORIGINS`. Основной API работает на токенах, но refresh-токен хранится в cookie, и эндпоинт обновления сессии принимает его именно оттуда. Для сценариев за обратным прокси с несколькими именами узла список доверенных источников нужен.

### С3. Внутренний API media доверяет заголовку `X-Forwarded-For`

В [core/media_api/src/media_server/views_internal.py](../core/media_api/src/media_server/views_internal.py) доступ разрешён при совпадении общего секрета и «частном» адресе клиента, но адрес берётся из заголовка, который может подделать клиент при прямом обращении к сервису. В сети Docker адреса вида `172.x` считаются частными, поэтому любой контейнер сети при знании секрета получает полный доступ на чтение и запись. Нужен список доверенных прокси и проверка фактического адреса соединения.

### С4. Запись через внутренний API без ограничения размера

`InternalWriteView` читает тело запроса целиком в память без верхней границы. Это путь к исчерпанию памяти и заполнению диска. Ограничение нужно такое же, как для обычной загрузки.

### С5. Содержимое загружаемых файлов не проверяется

Проверяется только расширение файла — при выдаче токена загрузки на стороне API и, если в токене указан список типов, на стороне media_api. Сигнатура содержимого не сверяется, антивирусной проверки нет. Файл с безобидным расширением может содержать что угодно.

### С6. Конфигурация nginx для Docker слабее, чем для обычной установки

Шаблон [core/deployment/docker/nginx/ergo_ms.docker.conf.template](../core/deployment/docker/nginx/ergo_ms.docker.conf.template) работает только по HTTP, не подключает набор защитных заголовков и ограничения частоты запросов, а служебный адрес проверки состояния media_api открыт без ограничения по адресу — в отличие от шаблона для обычной установки. Нужно привести конфигурации к одному уровню.

### С7. Роль «Пользователь» без групп получает все права просмотра

В [core/api/src/core/cms/adp/services/permissions.py](../core/api/src/core/cms/adp/services/permissions.py) (строки 562–594) при отсутствии у пользователя групп роли любой ключ права, оканчивающийся на `_view`, считается выданным. Это удобно при первичной настройке, но означает, что незаполненная конфигурация групп не ограничивает просмотр, а открывает его.

### С8. Объектные проверки прав нигде не формализованы

Метод `has_object_permission` не встречается в `core/api/src` ни разу. Проверки конкретного объекта выполняются вручную в `get_queryset` и `get_object` отдельных представлений. Работает это только там, где автор об этом помнил; для новых представлений нет ни базового класса, ни автоматической проверки.

### С9. Шаблон `.env` ослабляет настройки по сравнению с кодом

| Параметр | Значение в коде | Значение в шаблоне (было) |
|---|---|---|
| `API_THROTTLE_RATES_ANON` | `10/minute` | `100/minute` → затем `20/minute` |
| `API_PASSWORD_MIN_LENGTH` | 8 | 6 |
| `API_REFRESH_TOKEN_LIFETIME` | 1440 | 60 |
| `API_SWAGGER_ENABLED` | включено только в разработке | `true` |
| `API_DRF_BROWSABLE_ENABLED` | включено только в разработке | `true` |

Пароль по умолчанию не требует заглавной буквы и специального символа, регистрация открыта для всех. Шаблон, скопированный на сервер без правки, оставляет открытыми документацию API и просмотр эндпоинтов в браузере.

**Исправлено.** В `.env.example`: throttle anon/user как в коде (`10/minute`, `5000/hour`), пароль min 8 / max 128, Swagger и DRF browsable не заданы принудительно (дефолт кода по `ERGO_ENV`), CORS-комментарии требуют явный список в production, регистрация `open` с предупреждением для сервера. Refresh 60 минут оставлен намеренно (короче кодового запасного). Контроли `api.docs_exposure` / `password.policy` на уровне `standard`.

### С10. Двухфакторная аутентификация существует только как признак в профиле

У профиля есть поле `two_factor_enabled`, его можно переключить через настройки безопасности пользователя, но вход второй фактор не запрашивает. Реализации одноразовых кодов или ключей в ядре нет. Признак в интерфейсе создаёт ложное ощущение защиты.

### С11. Политика содержимого страниц зашита в код

Заголовок `Content-Security-Policy` формируется в [core/api/src/core/utils/middleware/security_headers_middleware.py](../core/api/src/core/utils/middleware/security_headers_middleware.py) и включает `unsafe-eval` и `unsafe-inline` ради внешнего картографического сервиса. Настроить политику через переменные окружения нельзя, поэтому установка, которой карты не нужны, всё равно работает с ослабленной политикой.

## Низкие находки

- **Н1. Первичные ключи в ответах административного API.** Список пользователей отдаёт `user_id` наряду с `public_id`, назначение роли принимает числовой идентификатор в теле запроса, регистрация возвращает `user_id`. Доступ ограничен администратором, но это расходится с принятым в проекте правилом отдавать наружу только `public_id`.
- **Н2. Cookie-подсказка о наличии сессии доступна сценариям на странице.** Cookie `ergo_session` намеренно не помечена как недоступная сценариям, чтобы клиент не делал лишних запросов. Секретов не содержит, но раскрывает факт наличия сессии.
- **Н3. Подпись ссылки на файл не покрывает параметры запроса.** Подписывается строка «путь и срок», поэтому параметр принудительной загрузки можно изменить при действительной подписи. Опасные типы содержимого всё равно отдаются как вложение, поэтому влияние ограничено.
- **Н4. Ошибки занесения токена в чёрный список подавляются.** В `session_devices.py` исключения при работе с чёрным списком проглатываются, и отзыв может незаметно не выполниться.
- **Н5. Имя пользователя записывается в журнал аудита при неудачном входе.** Событие `auth.login_failed` сохраняет введённое имя. Это полезно для расследований, но требует ограничения доступа к журналу, поскольку туда попадают в том числе опечатки в виде паролей.
- **Н6. Записи об устройствах не удаляются.** Для журнала клиентского мониторинга срок хранения настраивается, для устройств пользователей — нет; записи накапливаются, пока сессию не отзовут вручную.
- **Н7. Пример в документации API устарел.** Описание входа в Swagger показывает refresh-токен в теле ответа, хотя он давно передаётся только в cookie.

## Что уже сделано правильно

Эти решения стоит сохранить при доработках:

- **Токен на WebSocket передаётся первым сообщением**, а не в строке запроса, поэтому не попадает в журналы прокси и в заголовок источника перехода.
- **Access-токен на клиенте хранится в памяти**, refresh — в cookie, недоступной сценариям ([core/client/src/core/cms/js/tokenStorage.js](../core/client/src/core/cms/js/tokenStorage.js)); в браузерных хранилищах токенов нет.
- **Ссылки на файлы подписываются** с постоянным по времени сравнением подписи и ограниченным сроком действия ([core/shared/media_hmac.py](../core/shared/media_hmac.py)).
- **Защита от выхода за пределы хранилища многослойная**: нормализация пути и проверка принадлежности корню и на стороне API, и на стороне media_api.
- **Внутренний API media закрыт тремя условиями** одновременно: обязательный общий секрет, частный адрес и отсутствие маршрута в nginx.
- **Опасные типы содержимого всегда отдаются как вложение**, установлен запрет угадывания типа и запрет встраивания в рамку.
- **Публичные адреса используют `public_id`**, а не первичные ключи: карточка пользователя, административные операции над пользователем, клиентский мониторинг, пункты меню.
- **Проверка глобального администратора централизована** в `PermissionService`, роль и признак суперпользователя синхронизированы.
- **Журнал доступа не записывает строку запроса**, а в аудите маскируются поля с паролями и токенами.
- **Уведомления привязывают группу подписки к идентификатору пользователя** — подписаться на чужие уведомления нельзя.
